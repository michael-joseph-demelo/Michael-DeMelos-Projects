# Search results: `shield`

Shield logic is almost entirely in `characters/CharacterBase.gd`. `fists/FistBase.gd` handles what happens when a punch hits a shield. `NuggetDummy.gd`, `ThumbsUpFist.gd`, `ChainDrawer.gd`, `ChainLink.gd`, `DashTrail.gd` and `DamageNumber.gd` have no shield references.

## `characters/CharacterBase.gd`

### State variables
| Variable | Purpose |
|---|---|
| `is_shielding` | Main shield state flag |
| `shield_flow_in_progress` | Guard flag while enter/exit tweens are running |
| `can_dash_out_of_shield`, `dash_cancel_window` (0.05s), `dash_cancel_timer` | "Perfect dash cancel" after a successful block |
| `shield_transition_in_progress`, `shield_tween_left`, `shield_tween_right` | **Declared but never used** |

### Functions

**Input and flow**
- **`handle_shield_input()`**: Reads the `"shield"` input action. On press it calls `start_shield_flow()`. On release it calls `exit_shield_flow()`. It is skipped while `shield_flow_in_progress` is true.
- **`start_shield_flow()`**:
  1. Sets `is_shielding = true`.
  2. Tweens each non-disabled fist to `LBlockSlot` / `RBlockSlot` (0.15s) and reparents it there.
  3. Calls `spawn_shield_wall()` and waits a 0.05s buffer for tap-shields.
  4. Loops `while Input.is_action_pressed("shield")`, then calls `exit_shield_flow()`. It also exits early if both fists become disabled.
- **`exit_shield_flow()`**:
  1. Sets `is_frozen = true`.
  2. Tweens both fists back to their idle slots (0.25s) and reparents them.
  3. Calls `update_visual_state()` on each fist.
  4. Frees `ShieldWall` and clears the shield, frozen and flow flags.

**While shielding**
- **`_process_shielding_state()`**: Called from `_process()` every frame while shielding.
  - If both fists are disabled while in block slots, it forces an exit.
  - If one fist is disabled, it calls `_unblock_fist()`.
  - If a fist has recovered and is not in its block slot, it calls `_reshield_fist()`.
  - It always ends with `spawn_shield_wall()`.
- **`_unblock_fist(fist, target_slot)`** / **`_reshield_fist(fist, block_slot)`**: Tween one fist (0.15s), reparent it, and rebuild the wall.
- **`spawn_shield_wall()`**: Creates or reuses a `StaticBody2D` named `"ShieldWall"` under `$FistSlots/BlockSlots`.
  - Group: `"Shields"`. Collision layer: `1 << 1` (layer 2). Mask: `1 << 0` (layer 1).
  - Width: the sum of `render_width * sprite.scale.x` for the enabled fists. Height: 2.5.
  - Position: the midpoint between the block slots, plus a forward offset (perpendicular `* -8` with two fists, `(0, 8)` with one).
  - Visual: a translucent `ColorRect` (`Color(0.4, 0.8, 1.0, 0.3)`) and a `RectangleShape2D`.
- **`trigger_dash_cancel_window()`**: Opens the dash-cancel window. It is called from `FistBase` when a punch is blocked.

**Effects on other systems**
- **`_process()`**: Calls `_process_shielding_state()`. When not shielding, it frees any leftover `ShieldWall`.
- **`handle_movement_input()`**:
  - Handles the dash cancel: removes the wall, snaps the fists back to their slots, and calls `start_dash()`.
  - Otherwise sets `velocity = Vector2.ZERO` while shielding.
- **`handle_fist_inputs()`**, **`start_dash()`**, **`start_roll()`**: Return early while shielding.
- **`update_animation()`**: Forces the `"idle"` animation while shielding.

## `fists/FistBase.gd`

- **`_on_hitbox_body_entered(body)`**: Runs the block check when `body.is_in_group("Shields")`.
  - **Facing test:** `punch_dir.dot(body.global_transform.y) < -0.3`, meaning the punch hits the front face of the shield.
  - **Stamina cost:** It walks up the tree to find the owner (a node with `left_fist` and `right_fist`) and calls `reduce_stamina(15)` on both fists.
  - **Dash cancel:** It calls `trigger_dash_cancel_window()` on the owner.
  - **Punch result:** The attacking fist calls `start_retraction_with_delay(0.2)`.
- **`render_width`**: Used by `spawn_shield_wall()` for the wall size.
- **`is_disabled`, `reduce_stamina()`, `disable_fist()`**: Drive the single-fist and both-fists-disabled shield behavior.

## Possible issues found while searching

1. **`exit_shield_flow()` can run twice.** `start_shield_flow()` sets `shield_flow_in_progress = false` before its hold loop. On release, two things then happen:
   - `handle_shield_input()` calls `exit_shield_flow()`.
   - On the next frame, the `while` loop in `start_shield_flow()` ends and calls it again.
   
   The result is two overlapping sets of tweens.

2. **Overlapping tweens in `_process_shielding_state()`.** Nothing guards `_unblock_fist()` or `_reshield_fist()` while their 0.15s tween is running. `_process()` starts a fresh call every frame, so several tweens can stack on the same fist. Also, when one of these awaits, the rest of that frame's `_process()` (rotation, layers, input) is suspended for that call.

3. **Dash cancel leaves `start_shield_flow()` running.** Its hold loop is still waiting. When the player later releases the shield, it calls `exit_shield_flow()`, which sets `is_frozen = true` for 0.25s. That can stop the player mid-dash or right after it. The dash-cancel snap also skips `update_visual_state()`.

4. **The dash cancel ignores `dash_cooldown_timer`.** Its timer also decrements with `get_process_delta_time()` inside `_physics_process`.

5. **Misleading comment in the facing check.** The comment says the shield faces "-Y local axis", but the code uses `global_transform.y` (+Y). It still works, because `fist_slots` is rotated so that +Y points toward the cursor. The comment is just wrong.

6. **Player is frozen on every shield exit.** `exit_shield_flow()` sets `is_frozen = true`, which stops `_process` and `_physics_process` for 0.25s. That may be intended as release lag.

If you want to change shield behavior, the main places to edit are `start_shield_flow()`, `exit_shield_flow()`, `_process_shielding_state()` and `spawn_shield_wall()` in `CharacterBase.gd`, plus the `"Shields"` branch of `FistBase._on_hitbox_body_entered()`. Those changes also affect the stamina functions and `ThumbsUpFist`, which inherits from `FistBase`.
